# AI build log

Shared log for AI collaborators. One entry per phase: what was built, what the reviewer found, what changed, what is open.

## Phase 1: scaffold, Docker, schema, auth, seed
**Built:** Next 15/React 19/TS strict scaffold, Postgres 16 on :5434 (with a `nostos_test` DB), and a Prisma schema with snake_case tables, cents, and timestamptz. The init migration adds hand-written triggers: `moderation_event` and `venue_cover_history` are append-only, and user content can't be deleted. Also built: scrypt auth with hashed-token DB sessions, httpOnly SameSite=Lax cookies, and an Origin check; a dev login page; a deterministic seed (60 users, 25 venues, ~4.6k reports incl. 30 days of hour windows, presence, RSVPs, follows, placeholder PNG photos, comments/replies, flags); and a Vitest harness (unit + DB-backed integration against `nostos_test`).
**Reviewer found (11):** hidden content could never be restored; ON DELETE SET NULL conflicted with the append-only triggers; user-content columns (created_at etc.) were mutable; flag.venue_id had no FK; sliding session expiry never refreshed the cookie; signup race returned 500; the throttle map grew without bound; the seed broke the 15-min rate limit across back-to-back windows; the "byte-identical" claim was false; the troll had default reputation; the seed wasn't a literal Friday.
**Changed:** a new migration adds a RESTORE action, drops the sticky-hidden trigger, adds immutability triggers for report/photo/comment, RESTRICT FKs, flag→venue FK, and a reply-shape CHECK. Sessions are now fixed 30-day. Signup P2002 now returns 409. The throttle map is pruned. The seed now uses each user once per venue-night with explicit timestamps. Added DB-guard tests and origin tests.
**Open:** troll reputation is set by the Phase 2 reputation job. The "literal Friday" point is a documented decision (DECISIONS.md), not changed.

## Phase 2: consensus engine + accuracy score
**Built:** `src/lib/consensus` (pure): decay, reputation clamp, latest-per-user, data floor, weighted mode/median, mismatch, verdicts, and reputation formula. `src/lib/accuracy` (pure): hour windows, qualifying rules, $2 tolerance, and the 5-window floor. `src/server/services/reputation.ts`: a scheduled job wired into `instrumentation.ts`, the CLI, and the seed. The seeded troll now ends at ~0.22. Also 40+ unit tests plus integration tests.
**Reviewer found (8):** the accuracy score could be dodged by the venue (null or mid-hour cover change skipped windows); reputation could be farmed by copying the displayed consensus; 30-day inactivity reset users to 0.5; the job ran in one long transaction; reportCount equalled userCount; the in-progress hour counted; the hidden-report filter was untested; reputation choices were undocumented. (Also self-found: the advisory lock was taken and released on different pooled connections.)
**Changed:** every official value during the hour must match, and null never matches. Reports are judged only against later peers, with one verdict per user/venue/metric/hour. 90-day lookback; users without verdicts keep their rep. Computation now happens outside the tx, then a short locked tx does a batched UPDATE. reportCount = live reports and userCount = distinct users. Only completed hours count. New tests. DECISIONS.md now has Consensus, Reputation, and Accuracy sections.
**Open:** none known.

## Phase 3: map, venue page, reporting, dev location simulator
**Built:** `src/server/services/venues.ts` read models: map list with vibe consensus, here/going/friends counts, and an activity score. The venue page separates the official panel (from the venue) from the live panel (from people), and includes the accuracy score, mismatch callout, a live feed of photos under 3h plus a collapsed "Earlier", and comments with nested labelled venue replies. `src/server/permissions.ts` holds the central checks. Report, photo, and comment services enforce a server-side 100m geofence and a 15-min per-type cooldown serialized by a Postgres advisory xact lock. Photos are magic-byte sniffed, capped at 5MB, stored via the storage interface, and served by an upload route that hides moderated photos from non-moderators. UI: full-screen Leaflet map (dark filter on OSM tiles), hollow "?" pins for no data vs solid pins for dead, a bottom sheet with Live now / Going tonight / Nearby sorts and friend badges, and one-tap reporting. The dev-only location simulator (tap map, or "put my fake location here") is compiled out outside development. Verified in the browser at 390px: report accepted, then 429 on repeat.
**Reviewer found (6):** the chunked upload was buffered before the auth and size check; venue name was interpolated raw into pin HTML (stored XSS once owners can rename); orphaned files when the DB insert failed; the venue page never refreshed, so photos could outlive 3h on screen; validation came before auth (400 instead of 401); cover input was cleared on error.
**Changed:** the upload route requires sign-in and Content-Length (411/413) before parsing. Pin strings are escaped. The file is written after the row inside the tx, and deleted if the commit fails (storage gained `delete`). Added `AutoRefresh` (60s + on focus) and `ExpiresAt` (a live photo hides itself at 3h). Auth is now checked before parsing in all services. The cover input is kept on failure.
**Open:** one integration run flaked once (a `user.create` wait of about 5s in reputation.test). It didn't reproduce in 3 reruns; I'm watching for it.

## Phase 4: presence, RSVP, follows
**Built:** `src/server/services/social.ts`. Presence upserts a single row per user when a ping arrives inside the 100m geofence; "here now" counts rows seen within 45 min. Venue accounts can't inflate their own counts. RSVP is keyed by `nightKey` (5am America/New_York rollover), so it resets nightly. Also follow/unfollow, profiles, people search, and a friends list. UI: presence ping plus "I'm going tonight" toggle on the venue page, `/u/[handle]` profiles with a follow button, and `/people` (search + friends out tonight). Browser check: toggling RSVP and checking in updated the counts live.
**Reviewer found (5):** the ping interval restarted on every GPS update, so a stationary user never refreshed and dropped out at 45 min; GPS jitter triggered excessive pings; `router.refresh()` was called inside a setState updater; one-way follows made "followers-only" plans effectively public (stalking risk); an outside ping left the user counted as here.
**Changed:** the ping loop was rewritten with a steady 5-min interval keyed on the venue, plus movement pings of at least 25m at most every 30s, and no side effects in updaters. **Plans and friends-going are mutual-follow only** (see DECISIONS.md). An outside ping clears presence at that venue. The seed makes the demo account's friends mutual. Tests updated and added.
**Open:** none known.
